# Guard System: Additional Enforcement

[Guard System](./guard-system.md)

## Also Enforced

- **Plan-mode block**: `EnterPlanMode`/`ExitPlanMode` are blocked - planning happens through the Wayfinder or Code Writer skill and plan records, not the platform's plan mode.
- **PR-ready check**: a PR shows the branch as the remote holds it, so a PR-opening gh call is blocked while the tree it shows has staged, unstaged or untracked files, or HEAD has no upstream or differs from it (the local remote-tracking ref; no fetch). The calls are `gh pr create`, `gh pr new`, `gh pr ready`, a `gh api` POST to `repos/OWNER/REPO/pulls`, and `gh api graphql` naming `createPullRequest` or `markPullRequestReadyForReview`; a REST PATCH of `draft` cannot ready a PR and is not one. The line is read as its shell reads it: PowerShell for the PowerShell tool and on Codex for Windows, bash for Claude Code's Bash tool, both ways when unknown, and also as PowerShell when a bash line uses PowerShell syntax (a backtick line continuation, `&` starting a line, `$env:`); a reading that loses a `--head` another reading names adds no call of its own. A call counts at command position: after `;`, `&&`, `||`, `|`, a line break, a group or a subshell, past `VAR=value` words, shell keywords and `env`, `command`, `builtin`, `exec`, `nohup`, `time`, `nice`, `timeout`, `sudo`, `doas`, `xargs`, `stdbuf`, `ionice`, `setsid`, `unbuffer`, `caffeinate` and `wsl` (the same reading the dydo-command rules use), with gh under any path, case or `.exe` and gh's `-R`/`--repo` before `pr`. A commit message, a `grep` pattern, a comment or a heredoc body quoting one does not count, but a command substitution runs its command, so a `$(...)`, or in bash a backtick substitution, anywhere its shell expands it (inside double quotes too, not single) is read like a direct call. The tree is the call's directory: the tool input's `cwd`, else Codex's `workdir` (a relative one under the payload's `cwd`), else the payload's `cwd`, else the project root, as when Codex sends none, and the refusal says which. A call naming its branch (`--head [OWNER:]BRANCH`, `gh pr ready BRANCH`, a REST `head` field) is checked in every worktree with that branch checked out instead; it is refused when none has it, or when git lists one it cannot open (a stale, prunable entry). The refusal names every tree it checked, the clean ones marked clean. A call acting on a repository other than the tree's `origin`, by host, owner and name (case and `.git` aside; github.com when no host is named), is refused: run it from that repo's checkout. That repository is the one gh picks: a `gh pr ready` PR URL, else the last `-R`/`--repo`, else an inline `GH_REPO`, else an inherited `GH_REPO`, with `env -u`/`--unset GH_REPO`, `env -i` and an empty `GH_REPO=` applied left to right; for `gh api`, the endpoint's (its URL host or `--hostname`), where a lone `{owner}` or `{repo}` takes its part from `GH_REPO` or the checkout's origin and the literal part is compared. A directory outside git is allowed, wrapped call or not. It stops an accident, not a bypass, so it decodes nothing: a `pwsh`/`powershell -Command`, `bash`/`sh`/`zsh`/`dash`/`ksh -c`, `cmd /c` or `/k`, `eval`, `iex`/`Invoke-Expression`, `env -S`/`--split-string`, `ssh` (its remote command) or `watch` whose command string, read the same way, makes such a call is refused unread, asking to run gh directly so the check can see it, and so is any `-EncodedCommand`. So is a line the check cannot finish reading (a bare `case` word in a `$(...)`, an unpaired quote) when it holds a partial PR call, or holds a nested part (a `$(...)`, a group, an expanding heredoc body) and the word `gh`, `pwsh` or `powershell` anywhere in its text, under any path, case or `.exe`, since an `-EncodedCommand` hides gh's word; without one of them, such a line makes no PR call. Aliases, functions and other programs are not followed. A Codex argv-array command in its shell envelope (`[bash|sh|zsh, -c|-lc, script]` or `[pwsh|powershell, options, -Command, script]`) is its script, checked as a direct call; any other array is refused when its program is a wrapper holding such a call or any of its words reads as one. A help request is no PR: `gh pr create`, `gh pr new` or `gh pr ready` given `--help` or `-h` as a flag of its own prints gh's help and acts on nothing (gh 2.88.1), while `--help` as a flag's value (`--title --help`) or after `--`, or a real call later in the line, still counts. The refusal names what failed and asks for [`dydo pr-ready`](./../reference/dydo-commands-delivery.md#dydo-pr-ready) there, whose `--body` also checks the body names its ticket and holds the reviewer's `PASS` block.
- **Merge-route blocks** ([DR 061](../project/decisions/061-agents-merge-only-into-feature-branches.md) decision 7): agents merge only through [`dydo merge`](./../reference/dydo-commands-delivery.md#dydo-merge), into a `feature/*` branch, and the default branch is the user's. Every caller, top-level or sub-agent, is refused these, under Claude's Bash and PowerShell tools and Codex's argv arrays:
  - `gh pr merge`, including `--auto`, `-R`/`--repo` before `pr`, and gh under any path, case or `.exe`. It is refused into any base, because the guard cannot read a PR's base offline.
  - `gh api` on `pulls/N/merge`, `pulls/N/merge-async` or `merges`, as a path or a URL, with any method.
  - `gh api graphql` with a field naming `mergePullRequest`, `enablePullRequestAutoMerge` or `mergeBranch`.
  - A default-branch change: `gh repo edit --default-branch`, or a `gh api` PATCH of `repos/OWNER/REPO` with a `default_branch` field.
  - A `git push` that updates `master`, `main` (in any case) or the branch the local `origin/HEAD` names. The pushed branch is each refspec's destination: `dst` of `src:dst`, else `src`, with `+` and `refs/heads/` dropped. `HEAD` or `@` stands for the current branch, and a glob counts when it matches a default name. `--all`, `--branches` and `--mirror` push every branch. With no refspec, the push goes to the current branch's upstream (`branch.<name>.merge`), else to the current branch.

  Git state is read offline, in the call's directory as the PR-ready check finds it, or in the directory `git -C` names there. State git cannot read resolves nothing, so it never blocks on its own. A named default destination blocks everywhere. The line is read as the PR-ready check reads it: the same shells, command position, substitutions and data rules. So `gh pr view`, `gh pr merge --help`, and a commit message, heredoc body or `grep` pattern quoting a merge all pass. So do `git push origin feature/x`, `git push -u origin DYD-1-x`, a `gh api` GET of a PR, and `dydo merge` in the worker lane. A wrapper's command string (`bash -c`, `eval`, `pwsh -Command`, `cmd /c`, `env -S`, `ssh`, `watch`) is read, and refused for the route it holds. A Codex bare argv array is read as the same words in a shell: gh or git as its program, or a wrapper holding a route, is refused, while another program's arguments are data, so a bare `["grep", "-rn", "gh pr merge", "."]` passes as it does in every shell. This differs from the PR-ready check, whose bare-argv rule (admiral ruling 2026-10-27) still refuses another program's word that reads as a PR call. Every refusal names `dydo merge`, and the push and default-branch refusals also say the default branch is the user's. The blocks run with the hard blocks, right after the dangerous patterns and before every nudge, so a refusal never arms a warn's marker. A conflicted merge's local push to its feature branch passes. Accepted residuals, since the guard stops accidents, not a bypass:
  - An `-EncodedCommand`, or nesting past eight wrappers, is not decoded. Inside a git tree the PR-ready check refuses it unread; outside one it passes.
  - A GraphQL query or API body read from a file or stdin (`-F query=@file`, `--input`) is not read.
  - Aliases, functions, scripts and unrecognised programs are not followed.
  - A push whose destination only git config sets (a `remote.<name>.push` refspec, `push.default`) is judged by the rules above alone.
- **Agent-tool notice**: invoking the platform's built-in `Agent` tool passes with a stderr reminder that sub-agent calls run anonymous and governed by the same three layers.

## Archive-before-delete guard

Use `dydo archive branch <name>` or `dydo archive worktree <path>` for deletion; `archive list` and
`archive restore <id>` inspect and recover retained work. These commands are allowed for ordinary
agents and subagents, with generated Codex prefix rules for `dydo` and `dydo.exe`.

Raw `git branch -D`, combined delete/force flags, `git update-ref -d refs/heads/...`, deletion pushes
(`--delete`, `-d`, `:refs/heads/...`, `+:refs/heads/...`), `push --prune`, `push --mirror` and plain or
forced `git worktree remove` are refused with an archive command hint. Supported global Git options
and absolute executable paths are examined through the existing shell reader, as is every segment
of a compound command. Nonforced `git branch -d` stays allowed absent another rule. Existing clean
internals remain a compatibility consumer. There is no global guard bypass or environment switch.
These guards prevent accidental destructive calls; they do not stop a rogue agent.
