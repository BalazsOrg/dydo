# Control Flow: Edges

[Control Flow](./control-flow.md)

## 5. Edges: the contract table

One row per contact. A sender's return must carry every field the receiver's Must-Reads consume;
a field read that nobody returns, or returned that nobody reads, is a finding.

| # | Edge | Channel | Sender returns or writes | Receiver reads | Status set |
|---|---|---|---|---|---|
| 1 | user → co-thinker | C | the idea | about, architecture, glossary, linear-workspace-standard | - |
| 2 | co-thinker → repository | F | a Decision Record; a glossary entry | - | - |
| 3 | user → `to-project` → Linear | C, L | the Project: title, summary, intent, decisions taken, out of scope, links to the DR, glossary entries, source FutureFeature | - | Project `Backlog` |
| 4 | co-thinker → Linear (atomic ticket) | L | a ticket with one Type, one Mode, outcome, owned paths, blockers, exact gates, base branch | - | `Todo` |
| 5 | user → admiral | C | the Project, at any stage | the Project, governing Decisions and pinned feature specs, every ticket contract, working-tree standard | - |
| 6 | map holder → Linear (chart) | L | through `wayfinder`: the map in the Project description; first tickets with one Type, a Mode where a captain holds the Type, the five fields or their Type's own template, and native blocking edges; Project-level Questions naming waiters, with priority | the Project, governing DRs, about, architecture, dydo-glossary, linear-workspace-standard | Project `Planning`; first tickets and Questions `Todo` |
| 10 | invoked admiral → user | C | the charted route, for approval | - | Project `Planned` |
| 11 | admiral → first Ticket Captain, Linear | R, L | commission to open `feature/<slug>` from the approved main SHA before claim; the map in the Project description; base branch and blockers on every ticket, priority on every HITL one; the final Merge Sub-ticket of every captain-held ticket that merges, created under it and blocked by the previous one in plan order | - | Project `In Progress` |

| 13 | user → ticket-captain (HITL, atomic, or any ticket without an invoked admiral) | C, L | the ticket key; assignment | the same | - |

| 16 | code-writer → ticket-captain | R, L, G | before code, only when needed: one comment naming the lanes or the inexact contract line; after: the `IMPLEMENTED` line with implement SHA, behaviour, red proof, the suites and static gates run with exits, blocker | - | - |
| 17 | ticket-captain → Sub-tickets | L, G | lane Sub-tickets with the parent's Type and Mode, disjoint paths and branches, or retained Bug stages with native ordering and serial path transfer; one Merge Sub-ticket per actual integration; a Question Sub-ticket for local fog | - | lanes `Todo`; parent `In Progress` |
| 18 | ticket-captain → reviewer(spec), optional, for one risk the contract records, before the code | R (spawn) | the record carrying the captain's contract | that text on the ticket, the five fields, base SHA, branch, worktree, owned paths | `In Review` → `Implementing` |
| 19 | ticket-captain → code-writer, or docs-writer for a documentation change (fix hop) | R (spawn) | the ticket, the candidate, the review block that sent it | the ticket, the block, governing Decisions and pinned feature specs, standards | `Implementing`, on the FAIL's blockers |
| 20 | code-writer or docs-writer (fix hop) → ticket-captain | R, G | ticket key, fix SHA, each blocker with what closed it, any label changed with its evidence, gates rerun | - | - |
| 21 | ticket-captain → docs-writer | R (spawn) | the docs ticket and governing intent; for an Inquisition's record, its record path and the pushed findings register | the ticket, the register for a record, about, writing-docs, working-tree standard | `Implementing` |
| 22 | docs-writer → ticket-captain | R | ending commit SHA, files changed, what each says and why, witnesses, `dydo check` and gate results | - | - |
| 23 | ticket-captain → reviewer(code \| docs) | R (spawn) | rubric name, `Contract: <KEY> description as of <Linear updatedAt>`, Candidate SHA, Base SHA, the writer's `IMPLEMENTED` line | the contract as of that `updatedAt` with outcome, scenarios, owned paths, gates; the rubric; the hops; the `IMPLEMENTED` line, rerun only on a stated doubt | `In Review` |
| 24 | reviewer → ticket-captain, record, PR | R, L, G | the review block in the standard's one-line `PASS` or `FAIL` form, every finding with its severity; observations after it | - | `Implementing` on FAIL, one or more blockers |
| 25 | ticket-captain → Merge Sub-ticket (one per lane) | L, R (spawn), G | the lane branch at its PASS SHA; a code-writer maps conflicts and gates, merges it into the parent, a resolution that refactored leaving its code no worse than either side, then a fresh `reviewer(merge)` over the parent | the Merge template's fields: source, target, combined gates | lane `Ready to Merge` at its PASS, `Done` when merged; after the last, parent `In Review` for the review of the whole |
| 26 | ticket-captain → admiral | G, L, R | the PR into the feature branch with the block; `done <key>: PR ready` | the record | parent `Ready to Merge` |
| 27 | admiral → ticket-captain | R (message) | `merge`, when the Merge Sub-ticket's blocker clears, after re-wiring the order when a later PR was ready first; or a fresh commission from the record | the Merge Sub-ticket, the PR, the feature SHA | - |
| 28 | ticket-captain → Merge Sub-ticket (into the feature) | R (spawn), G | a code-writer maps the conflicts and combined gates, merges `--no-ff` and resolves, a resolution that refactored leaving its code no worse than either side, then a fresh `reviewer(merge)` over the integrated feature | the merge commit, both parents, the landed ticket's gates, governing Decisions and pinned feature specs | Sub-ticket and primary `Done` on PASS |
| 29 | reviewer(merge) → ticket-captain, Merge Sub-ticket | R, L | the review block naming the merge commit and the gates rerun | - | - |
| 30 | ticket-captain → admiral | R, L | `done <key>: merged`; worktrees and branches cleaned | - | - |
| 31 | map holder → Linear | L | new, split, dropped or resequenced tickets and Project-level map-holder-held tickets; reconciled ticket contracts and feature specs | the user approves a change to destination, scope, acceptance or architecture | - |
| 32 | admiral → Linear, user (inquisition proposal) | L, C | an Inquisition Ticket under the Project: the feature SHA and the cost; the commission question: a provider and model per phase, the swarm width, the Codex cap, the crew context limit; a project with a runnable surface and no verification skill needs one first | - | `Backlog` |
| 33 | user → Linear, admiral (inquisition confirmation) | L, C | the Inquisition Ticket moved to `Todo` with the commission answers, or `Canceled` with the reason; the user tells the admiral | - | `Todo` |
| 34 | admiral → ticket-captain (inquisition) | R (spawn), L | the Inquisition Ticket key; assignment | the ticket and its commission, the governing intent, the integrated feature SHA, working-tree standard | - |
| 35 | inquisition captain → Linear, Git | L, G | `## Scope` with the commission inputs; `inquisition/<slug>` off the audit SHA, never merged, its `inquisition-register.md` pushed; the area map on the ticket, every phase cell `yes` or a one-line reason; `released <key>: verification skill first` instead, when a runnable project has none | the admiral reads the release as the user's verification-skill need | `In Progress`, or released `Todo` |
| 35a | inquisition captain → Linear, admiral (above about 10 areas) | L, R | group Sub-tickets with the Inquisition Type, the parent's Mode and commission, their map rows and `inquisition/<slug>-<group>` branches off the audit SHA; the parent blocked by every group; this round's nit ticket; `released <key>: groups <keys>` | the admiral commissions one captain per group, each running its rows and closing with its register pushed, then resumes the parent for the cross-group triage | parent released `Todo` |
| 36 | inquisition captain → inquisitors | R (spawn) | one agent per area per phase, each its own session through T3 `delegate_task`: its map row and register entries, the audit SHA and landing base, the governing intent, the context limit, the worktree; for Break, its proof branch and test paths; for Drive, the verification skill and API base | the brief, the phase checklist, context-size, about, architecture, coding-standards | `In Progress` |
| 37 | inquisitor → inquisition captain | R, G | the fixed return: phase, area, items handed back, context against its limit; each finding with area, severity, `file:line`, wrong outcome and proof, or a `testable` or `drivable` tag; sightings under register IDs; not-reproduced hypotheses with the deciding observation; unreachable journeys with prerequisite and route tried; Break's red tests committed on its proof branch | - | - |
| 38 | inquisition captain → Git, inquisitors (routing) | G, R (spawn) | every return in the register, pushed before the next dispatch; duplicates joined as sightings; a tagged finding routed to the phase that can prove it, a short follow-up agent when that phase already ran; a fresh agent for the rest of an area handed back | - | - |
| 39 | inquisition captain → Linear, Bug captain (triage) | L | each severity checked against the source; a proven blocker or should as a Bug under the Project, feature base, its proof in `## Reproduction` (red-test SHA, quoted passages, definition and search, or rerunnable drive steps), Inquisition link, unassigned, or assigned to the inquisition captain and naming its patch branch when the patch lane will fix it; a verification gap as a should for `maintain-verification-skill`; a nit as one line on the round's nit ticket; a judgment call as a Question | the Bug captain reads the reproduction as normal-chain input | Bug status and blockers as `skills/roles/officers/ticket-captain/resources/inquisition.md` sets them |
| 40 | inquisition captain → code-writer (patch lane) | R (spawn), G | a proven, well-defined blocker or should: the Bug's own branch `<BUG-KEY>-<slug>` off the audit SHA, the red-test commit cherry-picked, then the fix that turns it green; branch and SHA attached to the Bug, then the Bug unassigned; a failed lane records its reason on the Bug and unassigns it without a patch | the Bug's captain verifies and reviews it once, in the Bug's own chain | - |
| 41 | inquisition captain → Git, Linear (sweep closed) | G, L | every applicable phase of every area returned; every register row with its final disposition; register and proof branches pushed; each open Bug's reproduction SHA on a pushed independent ref, its proof or patch branch, retention owned until its Bug captain adopts it | - | - |
| 41a | inquisition captain → docs-writer, reviewer(docs) (record) | R (spawn), G | on the Inquisition's own ticket branch from the feature tip: `dydo/project/inquisitions/<YYYY-MM-DD>-<slug>.md` from the pushed register, then a fresh docs review | the register, the ticket, writing-docs | `Implementing`, then `In Review` |
| 41b | inquisition captain → admiral | G, L, R | the record's PR into the feature with its PASS block; `done <key>: PR ready`; then its Merge Sub-ticket as any Project ticket's | the record | `Ready to Merge` |
| 42 | inquisition captain → admiral, Linear | R, L | after the record merges: the record at its path, every Bug filed and wired and every retained ref live, verified on the feature; the audit branch deleted; `done <key>: merged` | when this round found a blocker or a should, the admiral offers the next round once every such fix is `Done` | Inquisition `Done` |
| 43 | map holder → Linear (landing) | L | the landing Merge Ticket: `main` into the feature, gates, merge review with acceptance proof, the PR into `main`, the landing's walkthrough prepared | - | `Todo`, blocked by unresolved prerequisites for this landing: delivery, each confirmed Inquisition round, required fixes and every should-ticket; exclude self and later/deferred work; it lands only after a round with no blocker and no should |
| 44 | landing captain → Git, admiral | G, R | the PR into `main` with its PASS block; `done <key>: PR ready` | - | landing `Ready to Merge` |
| 45 | admiral → user → Git | C, G | the PR to click and the landing's walkthrough that follows; the feature merged into `main` as a merge commit, one Project at a time; the user tells the admiral, which resumes the landing captain to close and clean up the merged feature: `done <key>: merged` | - | landing `Done`, set by its captain |
| 46 | map holder → Walkthrough Ticket, user | L, C | the ticket, one per Milestone and the landing's last; `walkthrough` loaded by the map holder, then the four-part tour of the whole product, or the user's skip; only the walking skeleton's verdict holds back the work built on it, except overnight; at the landing, commission first fix Captain to re-cut the feature if findings reopen the lap | - | `In Progress` → `Done`; his verdict quoted or his skip recorded; findings as tickets; Project `Completed` when the landing's finds none |
| 47 | crew → ticket-captain (hand-raise) | R | the question, what was searched, why it blocks, facts or options found | - | - |
| 48 | ticket-captain → research | R (spawn) | the question and where the findings land | the question and destination, about, architecture | - |
| 49 | research → ticket-captain | R, L or F | one-line answer, destination, unsettled points; the report as a ticket comment or scratch file | - | Research Ticket `Done` by the map holder |
| 50 | ticket-captain → Linear (local fog) | L | a Question Sub-ticket under the delivery parent, wired as blocker, with its priority by the standard's guide; the record is the whole report | - | Question `Todo` |
| 51 | ticket-captain → admiral (Project-level fog, or any release) | R, L, G | `released <key>: <reason>`; prepared packet and resume SHA on the record, branch pushed, worktree removed, parent unassigned | - | parent `Todo`, blocker wired |
| 52 | admiral → Linear, user | L | a Project-level Question Ticket with homework, options, recommendation, wired to every waiter, with its priority by the standard's guide | - | `Todo` |
| 53 | user → Linear, repository, admiral | L, F, C | the answer on the ticket; a DR when it qualifies; the user tells the admiral | - | Question `Done` |
| 54 | admiral (every wake: a return, the user's word or its scheduled check-in) → Linear | L, R | commissions every pickable ticket, blocker-cleared ones included; re-wires the merge order when a later PR is ready first; resumes every Merge Sub-ticket whose turn came; re-sets priority on what waits on the user | the board | - |
| 55 | user → chief-of-staff | C | a request for triage | the board: open Questions, the gates, Projects in flight; working-tree standard | - |
| 56 | chief-of-staff → user, Linear | C, L | three lists with recommendations; mechanical fixes; delivery staged on its Project for the admiral | - | - |
| 57 | user → ticket-captain (takeover) | C via the admiral, or the sub-agent's transcript | `release`: the captain releases as in row 51; the user opens a top-level captain on the ticket | the record's resume point | parent `Todo` |
