# Scaffold a Project

## contract

- Contract each ticket from the spec sections it serves.
- [ ] Intent changes: update the spec first, then reconcile the affected contracts.

## docs

- [ ] Draft the working spec for `dydo/reference/working-specs/<project-slug>/<project-slug>.md` with the headings in `dydo/reference/feature-spec-convention.md` (from the repository root).
- It holds what the user agreed: the problem, the behavior, the decisions, what's out of scope and the acceptance checks.
- Keep his words where they matter.
- Put the draft in the Project description under `## Working spec draft`.
- [ ] The spec is on the remote: link it from the Project description and delete the draft.

## project

- [ ] Open by Method step 3, starting the check-in schedule first.
- Brief the first captain to commit the draft, unchanged, directly on `feature/<project-slug>` as its first commit, push it and post the SHA on its ticket, before it cuts its ticket branch.
- Before any commission, wire the first ticket as a native Linear blocker of every other first lane: `dydo survey` and the check-in Tick then see those lanes blocked until it is `Done`.
- Follow this checklist when you create a Project, or first chart one that has no working spec.
- [ ] Landing or cancellation: retire the spec by the convention's Retirement section.
- [ ] Settle the intent with the user (co-think, grilling, `to-project`), then create the Linear Project, or take the user's, naming you its map holder.
- The check-in finds a stalled or released first captain; resume or replace it from the draft.

## wayfinding

- [ ] Chart and get approval by Method step 2.
