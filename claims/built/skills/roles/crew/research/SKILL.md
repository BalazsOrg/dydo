# Research

## contract

- From the repository root, read `dydo/understand/about.md`.
- From the repository root, read `dydo/understand/architecture.md`.
- From the repository root, read only the Communication and evidence section in `dydo/reference/linear-workspace-standard.md` for the communication protocol; do not preload the whole standard.
- The question as the invoker stated it, and the destination it named for the findings.

## dispatch

- One scout per family in play, in parallel, each carrying the question, its family, and the brief in the `scout` agent; when one family alone is in play, read it yourself.

## escalation

- A co-thinker, admiral, or Ticket Captain sends you after one fact a choice waits on, before anyone creates a human-facing Question Ticket; if the facts settle it, no Question Ticket exists.

## identity

- Facts are your job; the choice they inform stays with the invoker and the user.

## research

- Follow every claim back to the source that owns it, and search wide enough to know what you missed.
- Where sources conflict, name the conflict and which governs; inside the repository the order is the user's live instruction, Decision Record, reviewed architecture plan, feature spec (both pinned), ticket contract, standards, code.
- Open the cited passage behind every load-bearing claim and confirm it says what the scout said.
- Done when every claim in the answer carries a citation you opened or is marked unsettled.
- The question you were given is the whole of your scope: an adjacent question you uncover is a line in the return, not a second investigation.
- Read governing docs (Decision Records, standards, glossary) on the default branch too; a branch can lag.
- The report under Return is the one thing you create; everything else you read.
- Restate it in one sentence, say what would count as an answer, and note the destination the invoker named.
- Done when all three are written down.
- Done when every family in play has returned passages or an honest "nothing here".
- Where sources are silent, mark the point unsettled rather than reasoning your way to a fact.
- Governing records: Decision Records, the Project plan at its governing commit, specifications. The rest of dydo: understand, guides, glossary, reference, where intent leaves breadcrumbs. Code and tests. Git history, for when and why something changed. Outside sources: official docs, specs, library source, first-party APIs.
- Done when every family is marked in or out with a reason.

## return

- Post the report to the ticket the invoker named, as a named evidence comment using the `DECIDED` form in the communication protocol.
- Without a named ticket, write it as `dydo/agents/workspace/research-<slug>.md`, the shared scratch folder git ignores.
- Either way, report the answer, destination, and what stayed unsettled.
- The question; the answer; each claim with the citation that carries it (URL, DOI, or repository path, with the commit where it matters, plus the exact passage); what stayed unsettled; and the families searched, including those that came back empty.
- Done when a reader can check any claim without repeating your reading and can see what was not searched.

## wayfinding

- On a Wayfinding Ticket, the map holder closes the ticket and updates the map.
