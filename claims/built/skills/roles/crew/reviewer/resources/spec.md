# Reviewing a Spec

## return

- **Return the review block.** PASS only when a writer can build it without being misled. **Done:** every finding states one material correction.

## review

- **Check the fog.** A missing answer is either found in the searched ground or returned through the Captain as a prepared Question packet naming its waiters. **Done:** no assumption bridges an unknown route.
- [ ] Any unanswered question records homework and blocks the work through the Captain
- **Check the proof.** Acceptance lines, scenarios and gates are exact and sufficient for the ticket outcome. Run those applicable before code; mark implementation gates `not run - pre-code` after verifying their commands and pass conditions. **Done:** the eventual result can fail as well as pass.
- [ ] Scenarios and exact gates can prove the outcome; only stage-applicable gates were run
- [ ] Edge cases, failures, migration, compatibility, and rollback are covered when consequential
- **Hunt hidden decisions.** Walk the contract as the delegated writer through behavior, files, seams, edge and failure handling, migration, compatibility, and proof. **Done:** no material choice is silently delegated to production.
- [ ] The acceptance lines account for every outcome without hidden design choices
- **Judge the scenarios.** Where the contract calls for Gherkin, each scenario stands at the product's boundary, in glossary words, deterministic, refining one criterion its parent carries; every example column changes an outcome. **Done:** the scenarios say what the ticket proves and nothing the parent did not ask for.
- [ ] Every scenario stands at the boundary, refines a parent criterion, and has no idle example column
- **Pin the ground.** Match the contract to the target ticket or direct lane Sub-ticket, its five contract fields, base SHA, branch, worktree, clean state and owned paths. **Done:** it binds the exact tree and nothing outside its authority.
- [ ] Exact Linear record, base SHA, branch, worktree, clean state and owned paths match
- Wording, formatting preference, and an equally valid route are outside this rubric: do not turn them into findings or notes.
- A scenario beyond its parent criterion, a concrete contract conflict, a false pattern, a hidden design choice, a consequential missing case, or a gate that cannot prove the outcome is a finding.
- Judge it against the parent's criteria, the settled working tree, the governing Decisions, pinned architecture-plan and feature-spec sections, and the `code-writer` skill.
- Target: the contract text on the ticket as it stands before any code, invoked when the Ticket Captain has bought a spec review.
- **Verify the ground it cites.** Read every cited Decision, specification, pattern, seam, file, and test at the base SHA. **Done:** each citation holds, or its departure is justified.
- [ ] Every cited Decision, pattern and path holds at the base SHA
